# Repository Guidelines

## Project Overview

Gradio extension for Stable Diffusion WebUI Forge (Forge Neo) that rewrites image-generation prompts with a local LLM. For each generation it spawns a transient llama.cpp `llama-server` (OpenAI-compatible HTTP API) on `127.0.0.1` at a random ephemeral port (49152-65535), sends chat-completion requests using an architecture-specific GGUF system-prompt preset, writes results back into the generation pipeline, then kills the server. Fully local - no cloud APIs, no persistent server.

## Architecture & Data Flow

- **Entry point**: `scripts/prompt_enhancer.py` defines `LlamaServerEnhance(scripts.Script)` with `sorting_priority = 999` and `scripts.AlwaysVisible`. NOTE: `sorting_priority` only orders the always-visible UI accordion section - it does NOT control `process()` call order. `process()` calls follow extension discovery order (alphabetical), which already puts sd-dynamic-prompts first; the callback-ordering instruction in `metadata.ini` (`LlamaServerEnhance` after DP's `Script` callback) makes that explicit, so DP always expands wildcards *before* enhancement and the extension never sees raw wildcards.
- **Import layout**: Forge adds the extension root to `sys.path`, so the sibling package `prompt_enhancer/` is imported as top-level (`from prompt_enhancer.client import ...`). Only `scripts/prompt_enhancer.py`, `prompt_enhancer/settings.py` and `prompt_enhancer/opts.py` import host `modules.*` - the rest of the package is host-independent (stdlib + aiohttp), which is what makes `test_llm.py` runnable standalone.
- **Generation flow** (`scripts/prompt_enhancer.py` `process()`): before anything else, `process()` takes `_ENHANCE_LOCK` non-blocking - the same lock the UI test button takes - because only one transient llama-server may exist at a time (two concurrent spawns would double the VRAM claim); on contention the generation is skipped with a console + debug-log notice. Then:
  1. `_free_gpu_memory()` - lazy Forge-only import of `backend.memory_management` (try/except so non-Forge installs degrade gracefully).
  2. `spawn_healthy_server()` (server.py; the entry's thin `_spawn_healthy_server` wrapper wires the debug log and the configured startup timeout) - build command, `Popen`, poll `/health`, discover model name via `GET /v1/models`, discover slot count via `GET /slots`, warm up the chat endpoint per slot.
  3. Enhance prompts via `flow.run_once` / `flow.run_per_image` (flow.py, host-independent; the entry wires settings + debug log into a `FlowContext`). "Per image" mode = one server, positive prompts batched in **strict buckets of the UI-selected bucket size** (`_batch_chat_completions`, aiohttp; a whole bucket finishes before the next starts; the accordion's *Bucket size* dropdown, *Auto (server slots)* = the discovered slot count, applies to positive and negative batches). With `vary_across_buckets=True` each bucket after the first gets the previous bucket's prompts (enhanced text, originals after failure) as a "do not repeat exactly, introduce variance" reference in the system prompt - so similar prompts across a multi-bucket batch don't collapse into clones. "Once" mode = single sequential request replicated across the batch. Negative prompts batched second, only for successfully enhanced positives, without a variation reference. The system prompt for every call is the preset plus `build_resolution_instruction()` (prompts.py: final `WxH` after hires fix, orientation, `A:B` aspect ratio via gcd, plus base dimensions when hires fix is active) - no DP wildcard note, since the extension runs after DP and never sees unexpanded wildcards. Negative enhancement is skipped with a console + debug-log notice when `negatives_ignored(resolved)` is true (`NEGATIVES_IGNORED_PRESETS` in presets.py: `flux-dev`, `flux-krea-dev`, `z-image-turbo` - those models have no negative-prompt conditioning). Misconfiguration skips are also announced in the console with a reason line: Forge UI preset with no LLM preset mapping, preset file missing, model path not set.
  4. The flow returns the enhanced prompt lists (or `None` when nothing was enhanced); the entry writes them back into `p.all_prompts` / `p.all_negative_prompts`. Failures keep the original prompt per index (graceful degradation). Server is killed in all paths (the flow's `finally`); `postprocess()` frees VRAM again.
- **Endpoints used** (all on `http://127.0.0.1:<port>`): `GET /health`, `GET /v1/models`, `GET /slots?model=`, `POST /v1/chat/completions` (`Authorization: Bearer no-key`, no inference params - server defaults).
- **DP interop / fixed order**: the extension always runs after sd-dynamic-prompts (alphabetical discovery order, made explicit by the callback-ordering instruction in `metadata.ini`), so the prompt it enhances is already expanded and the LLM never sees raw wildcards. `escape_accidental_dp_syntax()` (escape.py) then replaces `|` with `,` inside variant blocks the LLM newly invented - nothing expands tokens after this point, so unescaped they would reach the model verbatim. Tokens already present in the input prompt, and variants containing wildcard syntax, are preserved; custom separators are read defensively from DP settings via `opts.read_dp_separators()` and passed to `FlowContext.escape`, so every enhanced (positive and negative) output is escaped.
- **Preset resolution** (`prompt_enhancer/presets.py`): `presets/*.txt` files, name = filename stem (kebab-case). `Auto` mode maps `shared.opts.forge_preset` via `FORGE_TO_PRESET_MAP` (`flux`-`flux-dev`, `zit`-`z-image-turbo`, `anima`-`anima`), with checkpoint-substring overrides (`FLUX_CHECKPOINT_OVERRIDES`, e.g. `krea`-`flux-krea-dev`). `NEGATIVES_IGNORED_PRESETS` (frozenset) + `negatives_ignored(name)` mark presets whose models ignore negative prompts; `process()` skips the negative step for them.
- **Debug log**: `enhance_debug.log` in the extension root, written via `RotatingLog` (logfile.py, thread-safe) and rotated to `enhance_debug.log.1` at 5MB; llama-server stderr streamed in as `[llama-server]` lines. Gitignored.

## Key Directories

- `scripts/` - Forge extension entry point (Forge loads `.py` files here).
- `prompt_enhancer/` - logic package: `flow.py` (Once/Per-image generation pipelines against `FlowContext`), `server.py` (server process lifecycle + introspection), `client.py` (single chat request + shared retry policy), `batching.py` (strict-bucket concurrent completions), `escape.py` (DP syntax escaping), `negative.py` (negative-prompt instruction block + output validation), `prompts.py` (system-prompt assembly), `logfile.py` (rotating debug log), `opts.py` (host-dependent settings access), `settings.py` (UI options), `presets.py` (preset discovery/resolution).
- `presets/` - user-editable system-prompt `.txt` files, consumed verbatim.
- Extension root - `metadata.ini` manifest, `install.py` + `requirements.txt` (startup dependency install), `README.md`, standalone test scripts, `enhance_debug.log`.

## Development Commands

No build or packaging step. The extension is run by the host:

- Launch host (Windows): `webui.bat` from `C:\Dev\sd-webui-forge-neo` (auto-creates and activates `venv/`). Linux: `./webui.sh`.
- Standalone pipeline tests (from the extension dir):
  ```
  python test_llm.py --preset anima --model C:/models/my-model.gguf --dry-run
  python test_llm.py --preset anima --model C:/models/my-model.gguf --prompt "a cat"
  python test_llm.py --mode batch --preset anima --model C:/models/my-model.gguf --prompts "p1" "p2" "p3"
  python test_llm.py --server C:/tools/llamacpp/llama-server.exe --model C:/models/my-model.gguf --flags "-ngl 99 --temp 0.5" --timeout 60
  python test_llm.py --preset anima --model C:/models/my-model.gguf --startup-timeout 120
  ```
  Live modes need the `llama-server` binary + a `.gguf` model; `--dry-run` only prints the built command.
- Logic tests: `python test_escape.py` (pure stdlib, exit code 0 on pass), `python test_install.py` (installer logic; stdlib + `packaging`, host `launch` stubbed), `python test_batching.py` (drives `_batch_chat_completions` against a fake local llama-server: bucket splitting, the strict bucket barrier, cross-bucket variance reference; needs the venv's aiohttp), `python test_flow.py` (drives `run_once`/`run_per_image` against the same fake-server pattern: Once/Per-image entry points, empty/failure handling, server-kill on all paths, negative-echo rejection; needs the venv's aiohttp), and `python test_negative.py` (pure stdlib, exit code 0 on pass; imports `prompt_enhancer.negative` directly).
- In-UI verification: txt2img/img2img accordion "LLama Server Enhance" - "Test server" button (live spawn + health + small chat; blocked while a generation runs).

## Code Conventions & Common Patterns

- **A1111 script pattern**: `ui()` returns a list of Gradio controls positionally matched by `process(self, p, ...)` (e.g. `return [enable, enhance_mode, bucket_size, enhance_negative]`). The `InputAccordion` open state doubles as the enable flag; a static `gr.HTML` hint above the accordion (created but NOT returned from `ui()`) tells users that closing it disables the extension.
- **Settings**: register via `shared.opts.add_option(key="llama_enhance_*", info=shared.OptionInfo(..., section=("llama_enhance", "LLama Server Enhance")))` in `prompt_enhancer/settings.py`; hook it with `script_callbacks.on_ui_settings(...)` at module import in `scripts/prompt_enhancer.py`. All config is Forge UI settings - the extension reads/sets no environment variables.
- **Defensive cross-extension access**: `getattr(shared.opts, "dp_parser_variant_start", "{") or "{"` - never hard-require other extensions' or Forge's options.
- **Error handling**: failures return a `ChatResult` with `.error` set rather than raising; `_is_transient_error()` classifies 408/429/5xx/network errors as retryable (max 5 attempts, backoff 3/6/12/24s) while deterministic 4xx fail fast.
- **Async patterns**: single requests use stdlib `urllib` (client.py); batch mode uses `aiohttp` + `asyncio.run()` with strict buckets sized to the UI-selected bucket size (a bucket barrier, not a free-running semaphore; default = the server's parallel slot count). Both retry loops share `_is_transient_error` / `_retry_backoff` / `_describe_error` / `_clean_http_error` (defined in client.py, parses the server's one-line message out of the OpenAI-style JSON error body instead of dumping raw JSON into the console).
- **Windows subprocess care (do not "simplify" away)**: `CREATE_NO_WINDOW` creation flags, and daemon pipe-drainer threads reading stdout/stderr into bounded 256KB buffers. Without draining, the Windows 4KB pipe buffer fills and the server's own logging threads block - `/health` stays 200 while chat hangs. Rationale documented inline in `prompt_enhancer/server.py`.
- **Logging**: `logging.getLogger(__name__)` for the WebUI console, `print()` for user-facing progress lines, `RotatingLog.write()` for the rotating debug log on every branch decision.
- **Module style**: `from __future__ import annotations`, `__slots__` on result objects, `_`-prefixed private helpers, module-level `threading.Lock()` guard (`_ENHANCE_LOCK`: one llama-server at a time, shared by `process()` and the UI test button).
- **Presets**: plain `.txt`, kebab-case filenames, content is the raw system prompt; mapping tables live at module level in `prompt_enhancer/presets.py`.
- **README is the living source of truth** - update `README.md` when features, settings, or commands change.

## Important Files

- `scripts/prompt_enhancer.py` (~428 lines) - UI (incl. the bucket-size dropdown, the static enable-by-accordion hint, the auto-preset note, and the test-server controls via `_build_test_controls`), `_ENHANCE_LOCK` (serializes `process()` and the UI test button - one llama-server at a time; taken non-blocking on both sides, so the test reports busy or the generation skips enhancement), preset/model-path validation + console skip notices (`_resolve_preset`), `FlowContext` wiring (`_make_flow_ctx` / `_build_generation_prompts`), Once/Per-image dispatch to `flow.run_once` / `flow.run_per_image` with write-back, UI "Test server" flow (`_test_server` / `_run_server_test` / `_check_server_prereqs` / `_test_chat`, blocked while a generation is enhancing or another test runs), VRAM freeing.
- `prompt_enhancer/flow.py` (~389 lines) - host-independent generation pipelines: `FlowContext` (settings-backed `spawn`/`kill`, DP separators, output sinks - all injected by the entry, which keeps this module testable), `run_once` (single request, positive then validated negative, one shared server), `run_per_image` (model/slot discovery, bucket resolution from the dropdown, warmup, strict-bucket positive batch, validated negative batch of the successful indices only), `parse_bucket_size` + `BUCKET_SIZE_CHOICES` (the entry's dropdown imports them back). Failures degrade per index; the server is killed in `finally` on every path.
- `prompt_enhancer/opts.py` (~148 lines) - host-dependent settings access: `read_request_timeout` / `read_startup_timeout` (both via `_coerce_timeout`: missing, non-numeric, zero or negative values fall back to the default with a warning), `read_server_path` / `read_model_path` / `read_extra_flags` / `read_dp_separators` (all defensive `getattr` reads), `build_system_prompts` (preset + resolution, positive and negative variants), `spawn_healthy_server` (settings + debug-log wiring around the server.py helper).
- `prompt_enhancer/prompts.py` (~101 lines) - host-independent system-prompt assembly: `get_effective_dimensions` (hires-fix math), `build_resolution_instruction`, `assemble_system_prompt`.
- `prompt_enhancer/logfile.py` (~50 lines) - `RotatingLog`: thread-safe timestamped debug log with one-generation rotation at 5MB.
- `prompt_enhancer/server.py` (~470 lines) - `spawn_server`, `spawn_healthy_server` (spawn + health wait via `_await_health` + outcome reporting in one; used by the entry and `test_llm.py`), `_wait_for_server` (prints a `... still loading (Ns / Ms)` heartbeat every 10s of waiting), `_PipeDrainer`/`_ServerProcess` (drained output pipes, `stderr_tail`), `_discover_model_name`, `_discover_slot_count`, `_warmup_chat_endpoint` (+`_warmup_slot`), `_build_command`/`_find_free_port`, `_kill_server`. Stdlib only.
- `prompt_enhancer/client.py` (~315 lines) - `ChatResult`, `chat_completion_request` (model discovery + warmup + one completion against an already-running server; the caller owns the server), `enhance_prompt` (all-in-one spawn-chat-kill convenience used by `test_llm.py`), sync `_chat_completion` (single-attempt `_send_chat_request` + retry loop), and the shared retry policy: `_is_transient_error` / `_retry_backoff` / `_describe_error` / `_clean_http_error` (one-line message from the JSON error body).
- `prompt_enhancer/batching.py` (~248 lines) - `_batch_chat_completions` (strict buckets; `vary_across_buckets` passes the previous bucket's prompts as a variance reference), `_run_bucket` (one bucket's concurrent requests), `_plan_buckets`, `_variation_reference_block`, and the async single-request path (`_send_chat_request_async`/`_chat_completion_async` + `_print_final_status`) running the same retry policy. Needs aiohttp.
- `prompt_enhancer/escape.py` (~148 lines) - DP escaping: `escape_accidental_dp_syntax()` (+`_escape_variant_block`, `contains_wildcard`, `extract_variant_blocks`, `find_matching_variant_end`). Separators are explicit parameters, so it is testable without the host; imported directly by `test_escape.py`.
- `prompt_enhancer/negative.py` (~130 lines) - host-independent negative-prompt helpers: `build_negative_instruction()` (the system-prompt block appended for negative calls: anti-echo, scene-tailoring, format rules, concrete example), `build_negative_user_prompt()` (the `POSITIVE:`/`NEGATIVE:` user message), and `validate_negative_output()` (rejects empty, multi-line, overlong (>300 chars), identical-to-original, marker-containing, or positive-echoing outputs; strips a stray leading `NEGATIVE:`/`POSITIVE:` marker). Pure stdlib - imported directly by `test_negative.py`.
- `prompt_enhancer/presets.py` + `presets/*.txt` (`anima`, `flux-dev`, `flux-krea-dev`, `z-image-turbo`); `resolve_auto_preset()` maps the Forge-Neo UI preset (+ checkpoint overrides); `NEGATIVES_IGNORED_PRESETS` / `negatives_ignored()` mark presets whose models have no negative-prompt conditioning (the negative step is skipped for them). `list_presets()` is harness-only - used by `test_llm.py`'s discovery step, not by the WebUI path.
- `prompt_enhancer/settings.py` - the 5 options: `llama_enhance_server_path` (default `llama-server` from PATH), `llama_enhance_model_path`, `llama_enhance_timeout` (default = `client.DEFAULT_REQUEST_TIMEOUT`, 120s), `llama_enhance_startup_timeout` (default = `server._SERVER_STARTUP_TIMEOUT`, 60s), `llama_enhance_extra_flags`. The OptionInfo defaults reference the module constants, so the registered defaults cannot drift from the `opts.read_*_timeout()` fallbacks.
- `metadata.ini` - manifest (`[Extension] Name = ...`) plus the callback-ordering instruction that pins our `process()` callback after sd-dynamic-prompts' `Script` callback (section name = the full callback name the host's `add_callback` builds: `<canonical name>/<script file>/<category>/<class name>`); install is file-based (`install.py`).
- `install.py` + `requirements.txt` - startup dependency installer. Forge's `modules/launch_utils.py run_extensions_installers()` runs each extension's `install.py` with the host venv's python at startup (unless `--skip-install`), **before** extension scripts are loaded, and installs any `requirements.txt` spec that is not satisfied (currently `aiohttp>=3.9,<4`, a hard import of `prompt_enhancer/batching.py` and `prompt_enhancer/client.py`). No-op when satisfied; re-checks every startup. Gotchas: the pip spec must be **quoted** in the `run_pip` command (the host's `run()` uses `shell=True`, an unquoted `<`/`>` becomes a cmd redirect), and the spec check uses `packaging.SpecifierSet` because the host's `requirements_met()` only understands `==` pins.
- `README.md` - install, settings table, preset mapping, test-script usage, reliability notes.

## Runtime/Tooling Preferences

- **Python 3.13.x** in the host Forge venv (the host warns on other versions; live bytecode is `cpython-313`). Run extension code with the venv's `python`, not a system one.
- **Dependency install**: no lockfile; the host's extension-installer mechanism does it - `install.py` installs the missing `requirements.txt` specs (`aiohttp>=3.9,<4`) into the host venv at every startup, before scripts load (see Important Files). Everything else comes from the host environment (`gradio==4.40.0`, Forge `modules.*` API). `aiohttp` is a hard dependency of `prompt_enhancer/batching.py` (imported by `client.py` and `flow.py`); if the installer is skipped (`--skip-install`) or fails, the extension fails to import at startup (the host reports `Error loading script` and disables it).
- **External binary**: a llama.cpp `llama-server` executable on PATH or in the server-path setting; `llama-cpp-python`/torch are NOT used by this extension. GPU behavior depends entirely on user-provided flags (e.g. `-ngl 99`).
- **Host-side tooling does not cover this extension**: host `pyproject.toml` configures ruff with `exclude = ["extensions"]` (and black line-length 1024) - no lint gate applies here. Keep the host's black line-length (1024) in mind when editing.
- **Git**: the extension dir is its own repository (remote `MaxKruse/sd-webui-llama-server-enhance`, branch `main`) nested inside the Forge repo - not a submodule. Commit granularly with Conventional Commits on short feature branches; keep `.gitignore` coverage for `enhance_debug.log*` and `__pycache__/`.

## Testing & QA

- **No formal test infrastructure**: no pytest suite, no CI, no coverage tooling. Do not run bare `pytest` in the extension dir - `test_llm.py`'s helper functions get collected and fail without live-model args.
- `test_escape.py` - deterministic logic tests (~40 assertions) for `escape_accidental_dp_syntax`. It imports the real function from `prompt_enhancer/escape.py` (separators are explicit parameters, no host imports needed), so it cannot drift from production.
- `test_batching.py` - deterministic tests (~42 assertions) for the batch pipeline, run against a fake local llama-server (stdlib HTTP, real aiohttp client, no model needed): `_plan_buckets` splitting, the strict bucket barrier (no request of bucket N+1 starts before bucket N finishes), the cross-bucket variance reference (bucket 1's enhanced prompts appear in bucket 2's system prompt; a failed slot falls back to its original prompt; later buckets reference the immediately previous bucket), the default no-reference behavior, `_clean_http_error`/`_describe_error` one-line extraction (object, legacy-string, non-JSON, empty, and long bodies), and the `_wait_for_server` startup heartbeat (against an alive-but-unhealthy local HTTP server - a dead port is too slow to time against on Windows, where refused connects take ~2s).
- `test_flow.py` - deterministic tests (29 checks) for `prompt_enhancer/flow.py`, run against a fake local llama-server (stdlib HTTP, real aiohttp client, no model needed; unregistered chat messages get HTTP 400 so unexpected requests fail loudly): Once-mode happy path (positive + negative, request order incl. per-call warmups), the reported positive-echoed-into-negative bug (rejected, original kept, on both the Once and Per-image paths), positive failure (original kept, server still killed), `skip_negatives` (no negative request), empty-prompt skipping (no spawn), Per-image mixed batch (success/empty/failure indices, negative sent only for successful positives, warmup per slot count). Imports `prompt_enhancer.flow` directly, so it cannot drift from production.
- `test_entry.py` - deterministic tests (15 checks) for `scripts/prompt_enhancer.py`: the host boundary (`gradio` + `modules.*`) is stubbed in `sys.modules` and the entry is loaded by file path (the `test_install.py` / `test_opts.py` precedent). Covers the one-server-at-a-time mutual exclusion in both directions (`process()` skips when a server test holds the lock; `_test_server` reports busy when a generation holds it), the pre-existing `shared.state.job` guard, the disabled path, and the once-mode happy path against a fake local llama-server.
- `test_opts.py` - deterministic tests (18 checks) for `prompt_enhancer/opts.py`: the host `modules.shared` is stubbed in `sys.modules`, the real module is imported. Covers timeout coercion (missing / non-numeric / zero / negative values fall back to the default with a warning; int and numeric strings pass through) and the server-path / model / extra-flags accessors (pass-through and missing-attribute fallbacks).
- `test_install.py` - deterministic tests (16 checks) for `install.py`: requirements-line parsing, spec satisfaction against the real environment (via `importlib.metadata`, no mocks), and `install()` no-op/install behavior. It loads `install.py` by file path with the host `launch` module stubbed in `sys.modules` (host `launch` only imports inside the webui); the stub records `run_pip` calls. Run with the venv's python (needs `packaging`, which Forge installs before extension installers run).
- `test_negative.py` - deterministic tests (21 checks) for `prompt_enhancer/negative.py`: instruction/user-message construction and `validate_negative_output()` - legit output passes, empty/multi-line/overlong/identical-to-original/positive-echoing/marker-containing outputs are rejected, stray marker prefixes are stripped. Pure stdlib; imports the real module directly (no host imports needed), so it cannot drift from production.
- `test_llm.py` - live integration harness: `--dry-run` needs nothing; single/batch modes spawn a real `llama-server` with a real `.gguf` and kill it after. Batch mode mirrors production: slot discovery, warmup, strict buckets, `--concurrency` to override the bucket size. The preset-discovery step (runs in `--dry-run` too) asserts that every name in `NEGATIVES_IGNORED_PRESETS` exists as a preset file, so a renamed preset cannot silently disable the negative-skip behavior. It imports only `prompt_enhancer.server`/`client`/`batching`/`presets` (plus transitive aiohttp).
- **Verification workflow for changes**: `python test_escape.py` for escaping logic; `python test_negative.py` for negative-prompt instruction/validation logic; `python test_install.py` when touching `install.py`/`requirements.txt`; `python test_batching.py` for batch pipeline logic; `python test_flow.py` for the Once/Per-image pipeline glue (entry-point behavior, failure fallback, negative-echo rejection); `python test_entry.py` for entry-level behavior (one-server-at-a-time lock, skip paths, once mode); `python test_opts.py` for settings-access logic (timeout coercion, defensive reads); `python test_llm.py ... --dry-run` for command construction; live `test_llm.py` run and/or the in-UI "Test server" button for end-to-end. Watch `enhance_debug.log` for pipeline decisions and streamed server stderr.
